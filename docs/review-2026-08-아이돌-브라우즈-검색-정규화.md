## 1차 — 내부 코드 리뷰 (code-quality-reviewer)

### 반영함

| # | 지적 | 조치 | 근거 |
|---|---|---|---|
| Major 1 | 구두점만 입력(`"---"`)하면 **전체 그룹**이 반환된다 (기존 동작 회귀) | `GroupService.searchGroups` 에서 "미입력=전체"와 "정규화 후 빈 문자열=0건"을 분리 | 실제 회귀가 맞다. `SearchText` javadoc 이 "전체 조회로 떨어지지 않도록"이라고 적어놓고 정반대로 동작했다. 로컬에서 재현·수정 후 `keyword=---` → 0건, 미입력 → 188건 확인 |
| Major 2 | `CONCAT('%', :param, '%')` 에 null 이 들어가면 **H2와 MySQL 결과가 정반대** | JPQL 에 `:normalizedKeyword IS NOT NULL` 가드 추가 (buncheol 2개 + group/member 3개 쿼리) | 직접 재검증함: 3행 테이블에서 **H2 3건 매칭 / MySQL 0건**. 테스트가 운영을 대변하지 못하는 상태라 가드 없이는 이 경로에 테스트를 붙여도 무의미하다 |
| Major 3 | 정규화 규칙이 5곳에 있고 **프론트와 이미 어긋남**(`·`) | ① 프론트 `normalizeGroupSearchText` 에 `·` 추가 ② Java ↔ DB 생성 컬럼 파리티 테스트 추가 | `NCT · DREAM` 이 백엔드 `nctdream` / 프론트 `nct·dream` 로 갈려, **서버가 매칭해 내려준 그룹을 프론트 랭킹이 탈락시키는** 실제 버그였다. 사본 자체는 없앨 수 없어(생성 컬럼은 함수 호출 불가) CI 파리티 테스트로 드리프트를 잡는다 |
| Major 4 | group 패키지 신규 JPQL 4개가 전부 미검증 | `JpaGroupRepositoryAdapterTest`(파리티·공백무시·null가드·정렬), `GroupServiceTest`, `BuncheolListQueryServiceTest` 3케이스 추가 | 지적대로 커버리지 0이었다 |

### 반영하지 않음

| # | 지적 | 판단 | 근거 |
|---|---|---|---|
| Minor 7 | `idx_group_members_name` 이 이제 미사용이니 제거 | **보류** | 지적은 맞다(유일 사용처였던 정확일치 `findAllByName` 이 사라졌다). 다만 인덱스 DROP 은 운영 DB 에 추가 ALTER 가 필요하고, 이번 배포의 핵심(검색 정규화)과 무관하게 롤백 표면을 넓힌다. 스토리지 낭비 외 해가 없으므로 **정리용 별도 PR** 로 분리한다 |
| Minor 8 | `IN (서브쿼리)` 와 `EXISTS` 스타일 혼재 | **미반영** | 혼재는 사실이나, `IN (서브쿼리)` 쪽은 이번에 건드리지 않은 **기존 memberId 필터**다. 동작이 검증된 쿼리를 스타일 통일 목적으로 바꾸면 이 PR 의 회귀 표면만 커진다 |
| Suggestion 1 | REPLACE 10중첩 → `REGEXP_REPLACE` | **미반영** | 리뷰 스스로 확인했듯 MySQL 은 `[[:space:]]`, H2 는 `(?U)[\s]` 로 **표현이 여전히 달라진다**. 중복 제거라는 목적을 달성하지 못하면서 검증된 DDL 만 교체하게 된다. 대신 파리티 테스트(Major 3)로 드리프트를 잡는다 |
| Suggestion 2 | `SecurityConfig` 를 `/v1/groups/{groupId:[0-9]+}` 로 좁히기 | **보류** | 방어 아이디어는 좋다. 다만 Spring Security 7 PathPattern 의 정규식 path variable 지원을 실제로 확인하지 않은 채 **인증 경계**를 바꾸는 건 위험하다. 현재는 `/v1/groups/*` 가 단일 세그먼트만 매칭해 인증 필요 경로(`/v1/groups/favorites/me`, 2세그먼트)를 건드리지 않는 것을 **로컬에서 401 로 실증**했고, 주석으로 불변식을 남겼다. 별도로 검증 후 적용 |
| Suggestion 3 | 1~2자 검색어일 때 멤버 id IN 리스트 상한 | **미반영** | 상한을 두면 결과가 **조용히 잘린다**(검색에서 가장 나쁜 실패 모드). 현재 규모는 멤버 1,070행이라 최악의 경우에도 IN 리스트가 수백 수준이다. 상한보다 캐싱이나 최소 길이 정책이 나은 해법이라 판단, 규모가 커지면 재검토 |

## 2차 — 브라우저 UI/UX 검증 루프 (5회)

코드 리뷰가 잡지 못한, **실제로 띄워봐야 나오는** 문제들.

| 루프 | 발견 | 조치 |
|---|---|---|
| 1 | "모집중 분철 0개" 와 "전체 분철 4개" 가 나란히 보여 모순처럼 읽힘 | 0건일 땐 "지금 모집중인 분철은 없어요" 문구로 전환 |
| 1 | **취소된 분철이 아티스트 페이지에 노출** — 유입 랜딩에서 취소분만 남는 경우 발생 | 사이트맵과 같은 기준(`isBuncheolCancelledStatus`)으로 제외 |
| 1 | 멤버 칩이 가로로 넘치는데 더 있다는 표시가 없음 | 오른쪽 페이드 추가 |
