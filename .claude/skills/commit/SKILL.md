# commit

현재 작업 트리의 변경분을 BuncheolEasy 컨벤션에 맞는 커밋으로 묶는다.

## 사전 컨텍스트 (동적 주입)

- 작업 트리 상태:
  !`git status`
- 변경 통계:
  !`git diff --stat HEAD`
- 스테이징된 변경:
  !`git diff --cached`
- 스테이징 안 된 변경:
  !`git diff`
- 최근 커밋 5개 (스타일 참고):
  !`git log --oneline -5`
- 현재 브랜치:
  !`git rev-parse --abbrev-ref HEAD`

## 절차

1. **변경 분석**
   - 변경 파일을 읽고 무엇이/왜 바뀌었는지 1~2 문장으로 요약한다.
   - **작업 단위로 분리 커밋이 기본이다.** 한 기능이라도 독립적으로 이해 가능한 단위(관심사/레이어/모듈 경계, 또는 순차적 작업 단계)가 여럿이면 나눈다 — 나중에 커밋 로그만으로 컨텍스트를 파악하기 쉽게 하는 것이 목적이다. 분리가 자명하면 묻지 말고 나눠서 커밋하고, 어떻게 쪼갤지 모호할 때만 제안 후 확인한다.
     - **분리 방법**: 파일 경계로 깔끔히 나뉘면 작업 단위별로 `git add <file>` 해서 순차 커밋한다. 한 파일에 여러 작업 단위가 hunk 단위로 섞여 있으면 `git add -p`(패치 분리)가 필요한데 **이 환경은 인터랙티브 입력이 불가**하므로, 그 경우엔 파일 경계로 깔끔히 나뉘는 **최대 단위**까지만 쪼개고 한계를 사용자에게 알린다(억지로 hunk 수술하지 않는다).
     - **순서/정합성**: 의존 방향대로 배치해 각 커밋이 가능하면 단독으로 빌드·테스트 green 이 되게 한다(예: 도메인/모듈 추가 → 그를 쓰는 통합 → 설정 플립).
   - 무관한 변경(이번 작업과 상관없는 설정/파일 수정)이 섞여 있으면 해당 파일은 커밋에서 **제외**하고 사용자에게 알린다(특히 `application.yaml` 의 `ddl-auto` 같은 위험 설정).
   - 비밀(.env, credentials, *.pem, application-*.yaml 의 시크릿) 이 staged 인지 확인. 있으면 사용자에게 경고하고 중단.

2. **메시지 작성**
   - 형식: `<type>: <한국어 요약>`
   - type: `feat` | `fix` | `refactor` | `chore` | `docs` | `test` | `ci`
   - scope 는 쓰지 않는다.
   - 제목은 50자 이내 권장, 한 줄. 마침표 없음.
   - 본문이 필요하면 한 줄 띄고 한국어 bullet 또는 단락. **왜** 가 자명하지 않은 변경에 한해 작성.
   - 다음 표현 절대 금지: `Co-Authored-By:`, `🤖 Generated with`, `Generated by AI`, 이모지 일체.

3. **스테이징**
   - 변경 파일을 **명시적으로** `git add <file> <file>` 로 추가한다.
   - `git add -A` / `git add .` 금지 (메모리/CLAUDE.md 정책: 시크릿·대용량 바이너리 사고 방지).
   - 새 디렉토리 안의 파일도 개별 경로로 나열.

4. **커밋 직전 안전 점검**
   - 작업 단위가 코드 변경(.java, .sql 등) 을 포함하면 **`code-quality-reviewer` 가 이미 수행됐는지** 확인 (CLAUDE.md 의 작업 단위 자동 리뷰 규칙). 안 됐다면 사용자에게 "리뷰 먼저 돌릴까요?" 묻기.
   - 다음 옵션은 사용자가 명시적으로 요청하지 않는 한 절대 사용 금지: `--no-verify`, `--no-gpg-sign`, `--amend` (이미 푸시된 커밋), `-i`.

5. **커밋 실행**
   - HEREDOC 으로 메시지 전달:
     ```bash
     git commit -m "$(cat <<'EOF'
     feat: 한국어 요약

     - 비자명한 결정 1
     - 비자명한 결정 2
     EOF
     )"
     ```
   - hook 실패 시 **새 커밋을 만들지 말고** 원인 fix → 재스테이징 → 새 커밋.

6. **결과 보고**
   - `git status` / `git log --oneline` 로 결과 확인.
   - 사용자에게 **각** 커밋의 해시 + 제목 한 줄(여러 단위로 나눴으면 전부) + 변경 stat, 그리고 커밋에서 제외한 파일이 있으면 그 사유를 보고. 푸시는 별도 지시 없으면 하지 않는다.

## 예시 (이 저장소 실제 사례)

| 좋은 예 | 나쁜 예 |
|---|---|
| `feat: 분철 공개 목록 조회 API 구현` | `feat(api): add buncheol list API` (영문 + scope) |
| `chore: PR 템플릿 추가` | `Add PR template` (prefix 누락 + 영문) |
| `fix: 백엔드 시간 처리 UTC 통일` | `[FIX] 시간 통일` (대괄호 태그는 PR title 용) |
| `refactor: 시간 호출 Clock 빈 주입 일관화` | `refactor: clock 주입 — Co-Authored-By: Claude <noreply@...>` (AI 서명) |

## 참고

- 대괄호 태그 (`[FEAT]` 등) 는 **PR title 용**. 개별 커밋 메시지에는 쓰지 않는다.
- 커밋 메시지에 PR 번호 (`(#21)`) 는 squash 머지 시 GitHub 가 자동으로 붙이므로 수동으로 넣지 않는다.
- 동시에 여러 type 의 변경이 묶이는 게 자연스러우면 main type 하나로 prefix 를 고르고, 본문 bullet 에 부수 변경을 적는다.
